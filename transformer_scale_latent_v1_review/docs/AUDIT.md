## 4. 输入字段来源与泄漏检查

模型输入窗口 33×57。实测非零列：
`[0,1,3,6,7,8,9,10,11,12,13, 24,25,26,27,28,29,30,31, 36,37,39,42,43,44, 48,50, 52,53,54,55]`。

| 列 | 含义 | 判定 |
|---|---|---|
| 0–17 / 18–35 | 各机器人的位姿、速度、可见性、中点、法向、距离、点数、置信、接触 | 该帧的**自身**观测 |
| 36–47 | 双方关系块（对方在该机器人 R_i0 下的位姿） | 该帧的公开观测 |
| **48** | **该帧的已执行时间** | 对历史帧是**过去值**；对最新帧即当前时钟，允许 |
| 49 | 该帧的控制器阶段 | 对历史帧是过去值，允许 |
| 50 | 是否首帧 | 过去值 |
| 51–56 | 候选命令（alpha0/1、速度0/1、active0/1） | 公开候选 |

**结论：没有未来字段进入输入窗口。**

关键澄清：真实退出时刻 `T_exit` 出现在 **terminal token 的第 48 槽**，而 terminal token
只用作监督标签，**从不拼进窗口**。历史 token 的第 48 槽是该帧自己的时间，不是 `T_exit`。
（上一轮曾有报告把两者混为一谈，这里以实测非零列为准。）

未来真实控制器阶段、未来实际低层控制、未来接触结果、未来真实位姿、物体真值、实际剩余时长
均不在输入中。

## 6. 100 次更新计时与显存（4 线程，CPU）

| 模型 | 参数量 | 秒/更新 | 更新/分钟 | 峰值 RSS | RSS 增量 |
|---|---:|---:|---:|---:|---:|
| 直接多步 Transformer | 1,469,952 | 0.763 | 78.7 | 1498.8 MB | 389.9 MB |
| latent 自回归 | 1,461,600 | 1.431 | 41.9 | 1839.3 MB | 340.5 MB |

**同参数量不等于同计算量**：latent 递推每次更新约 1.9× 于直接多步，因为要沿 8 步链反传。
调度据此确定：每批 128 不变，全部配置 3200 次更新，4 线程，最多 4 个进程并行。

## 7. 顺带发现并修复的工程问题

- 训练最初每次更新都从 token 数组重建全部窗口，`build_example` 的 Python 循环主导了步时。
  改为逐面板预计算并索引后，直接多步从 0.76 s/更新降到约 0.12 s/更新（**约 6×**）。
  缓存与现算窗口、mask、标签、未来张量逐项比对为**完全相等**（`cache.py`）。
- `LatentAutoregressive.forward` 原本把真实前缀编码了两次（rollout 内一次、终态头一次），
  已改为复用同一次编码。
- 容量曲线进程未应用 `--threads`，会独占全部核心并拖慢整个矩阵，已修。
