# 新 CAP 的原生 C++ 编写方案与 trace 接口

2026-11-19 · 设计提案，待原型验证。

下一批新 CAP 拟由 LLM 直接用 C++ 编写完整策略。开发验证、闭环执行、蒸馏采样与 trace 采集复用同一份冻结策略。先用一个新 CAP 验证编写成本、逻辑正确性和整条执行路径的效率，再决定是否将 C++ 设为新策略的默认语言。历史 Python/Cython CAP 继续作为已有实验的冻结基线。

现有证据来自七 CAP 路由器。仅将共用的 `clearances` 和 `navigate` 数值循环移入 C，12 个预热进程跑同一批 24 个场景的平均墙钟就从 17.77 秒降至 10.78 秒。整份策略采用 C++ 后的耗时、以及 LLM 在相同开发预算内能产出怎样的策略，仍待测量。[配对测速报告](../../outputs/semantic_rl/cap_shared_kernel_20261119_01/REPORT.md)

## 策略与宿主各自负责什么

宿主提供版本化头文件，定义只读公开观测、上次实际执行动作与反馈、策略记忆、动作提案和 trace 写入接口。每个决策边界只打包一次观测，各 CAP 读取同一份真实历史前缀，各自更新记忆。即使上一轮选中了其他 CAP 的动作，本轮各 CAP 收到的也是实际发生的执行反馈。每个 episode 开始时重置各自的记忆。

LLM 编写完整的感知处理、几何计算、搜索和动作选择。宿主负责观测投影、动作合法性检查、执行期预算、编译与进程隔离，在常驻 worker 中复用编译产物。作者沿用 `authoring_v2` 的公开技能说明和开发预算。冻结时记录策略源码、接口及 trace schema 版本、编译器和编译选项，评估前核对冻结清单。[作者入口](../../experiments/planar_tasks/authoring_v2/README.md) · [现行 CAP 编译契约](../../experiments/planar_tasks/semantic_rl/typed_compiler.py)

## 每份策略默认预留 trace 接口

- **采集开关由宿主管理。** 策略模板始终提供只写接口，例如 `trace.scalar(slot, value)`。普通运行默认关闭采集，写入操作为空操作。开启时使用同一份策略产物和决策入口。策略只能提交本步已经求得的值，不能读取记录器状态或依赖写入结果选择动作。
- **每个决策边界单独记录。** 槽位随策略版本冻结，并登记程序位置、含义、类型、来源与适用机器人。建议首版对标量保留本边界最后一次有限值，对分支或返回记录实际经过的位置。每步重置有效掩码，区分“本步未经过”和“本步值为零”。这些记录只使用策略当时依法可见的输入和中间计算。
- **标明 trace 的来源。** 模板允许作者显式记录规划代价、可行方向数等量；后续自动插桩也可通过同一接口写入分支或局部变量。两类槽位在 schema 中分别标记，以便单独消融。原有 Python trace 由 AST 自动插桩产生，跨语言比较需要另行说明槽位语义。[现有插桩实现](../../experiments/planar_tasks/semantic_rl/program_trace_value_v1/instrumentation.py)

## 原型验收和后续研究

1. **先验证一个新 CAP。** 记录生成、编译和修复成本，检查输出动作合法性及开发场景的逐例成败。用固定公开历史重放，对比开启和关闭 trace 时每一步的提案、动作和下一步策略记忆，再用相同初态核对闭环结果。原生策略可以直接按上述契约验收，无需为每个新 CAP 另写一份 Python 实现。
2. **测实际执行成本。** 分开记录首次编译、预热后的策略调用、完整 episode 墙钟和 trace 采集开销。整段测速包括输入打包、进程通信、环境推进及回放写盘。报告决策数和实际 ticks，避免把不同策略的提前结束误计为语言加速。
3. **保留同一批策略上的 trace 消融。** 冻结 CAP、候选动作、开发数据与场景划分。路由器基线读取公开输入与动作建议，对照组再读取指定来源的 trace。按同一批留出初态配对比较成功率，以及单 CAP 成功并集中混合策略保留、丢失的场景数。这样可以单独检验中间计算是否提供了动作建议之外的价值。
