# D013 option testbed — handoff / diagnostic request (2026-11-03)

## 1. Scope

Work is on the D013 option testbed only (`http://127.0.0.1:8765/`, controller `m3b`).
No RL training, no learned model, no true-contact sensor. Contact is estimated from
`patch_gap <= 0.02`; privileged object pose is used only for testbed rendering/evaluation,
never for controller observations.

The current testbed process is intentionally left in the **full-lock experimental state**
for inspection. It is not presented as a successful final configuration.

## 2. What currently works (stable baselines before the last experiment)

- `LIDAR_RANGE = 5.00 m`.
- Simple hierarchical selector as default:
  - one robot: support midpoint;
  - two robots on the same face: 1/3 and 2/3, enforcing `2R + margin`;
  - different faces: each face midpoint;
  - no `o_ref`-based q descent for the simple selector.
- Stable approach-lock configuration (before the current full-lock experiment):
  - approach: first selector result locked;
  - contact/push: selector unlocked;
  - q prediction from direct contact velocity;
  - q' offset retained.
  This gave:
  - N+E goal fixed: 105–122 ticks, success;
  - south push: 530 ticks, success;
  - approach east: 91 ticks, success;
  - single east: 95 ticks, success;
  - dual north: 87–119 ticks, success.

## 3. Changes by area

### 3.1 Lidar

- `src/coimagine/random_start/spec.py`: `LIDAR_RANGE 1.80 -> 5.00`.
- Testbed scene, lidar and UI use the same range.

### 3.2 Support memory

`experiments/option_rl_v19/unknown_shape.py`:

- `SupportMemory` stores fitted support lines `(n, rho, lo, hi)`, not raw patches.
- During non-contact/static ticks it calls `calibrate(observations)`:
  - uses only current patches from **both** robots;
  - requires `span_m >= .04`, at least 3 points;
  - clusters by normal/rho and PCA-fits one line per cluster;
  - old memory endpoints are no longer fed back into calibration.
- During contact it freezes memory.
- Observed result: octagon memory stabilised at 3 lines at ticks 100/300/500/700
  (previous 9 -> 18 lines). N+E 102–122, south 530.

Current limitation: memory only retains currently visible/calibrated faces. Faces that
disappear are not persisted with an explicit identity/expiry policy.

### 3.3 EKF and direct contact solver

- `RigidMotionEKF` has an SVD null-space prior: unobservable twist directions are
  pulled to zero with a soft covariance prior.
- `SharedMotionEstimator._try_direct` implements a contact-point-reference solve:
  - contact points `q_i = own_i + n_i * R`;
  - first contact as reference;
  - rows `H1=[n1,0]`, `H2=[n2, n2·J(q2-q1)]`;
  - optional `dphi` row;
  - rank/condition/residual gating;
  - output `contact_solution` with per-contact `q,n,v`.
- Important semantic warning: the EKF state is a twist at the fixed world origin;
  the direct solver output is naturally at a contact point. Earlier audits mixed
  object-centre velocity with world-origin twist and are not safe to compare directly.
  Any further error audit must state the reference point explicitly.

Historical diagnostic numbers (useful, not current guarantees):

- N+E direct contact solve: contact-point velocity error ~`.0103 m/s` mean,
  p90 `.0181`; omega ~`.0195 rad/s`.
- Direct translation was much better than the centre-referenced EKF comparison
  (`.016` vs `.246`), but that comparison used different reference semantics;
  treat the number as a diagnostic, not a controller claim.

### 3.4 q / q' / selector state

- `q` is the selector candidate; `q' = q + t*contact_offset`.
- `contact_offset` is integrated from yaw error, clamped to ±.06.
- `D013_USE_QPRIME` default is `1` (q' control). `D013_USE_QPRIME=0` gives q-direct.
- `D013_SIMPLE_SELECTOR` default is `1`.
- A support-relative anchor was added for q:
  - first selector stores face `n/rho`, support, `u=q_t-support_center`;
  - subsequent q correction attempts to map to the current support.
- A later experiment (current testbed) made the selector run **once per option**
  (env-level commit), then q is updated by current visible-face candidates and/or
  anchor correction; q prediction is skipped when committed.

## 9. Exact open questions for planning

1. **q jump source**: instrument every q write (`nearest`, `single committed`,
   `selector`, `_last_alloc`, q' base). The current `.10 m` hysteresis should have
   held q; it did not. Find which path overwrites it.
2. **Face identity**: for octagon, q moves between adjacent faces and between
   same-normal disjoint support segments. Decide whether q must carry a stable
   segment/face id, with explicit invalidation, or whether visible support should
   be pruned by segment continuity.
3. **Full lock vs contact unlock**: full lock currently fails N+E/dual and octagon;
   stable baseline required contact selector. Decide whether full lock is a hard
   requirement or whether a face/segment lock with contact q correction is enough.
4. **Polygon task**: fix/choose a task sequence for T/triangle/octagon; currently
   only smoke/physics works, all task runs false.
5. **Memory persistence**: current calibration uses only current visible patches;
   decide whether unseen faces must be retained with an explicit identity/expiry.
6. **Reference semantics**: any new velocity error audit must compare at the same
   reference point (origin twist vs contact point). Do not reuse the earlier
   centre-vs-origin comparison as a controller claim.
