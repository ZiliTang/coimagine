## 5. 诊断需要回答的问题

围绕**这一条轨迹**按先后回答，允许存在多个相互作用的问题：

- 换面结束究竟把机器人放在哪？开始 PUSH 时法向、支持、q、own、e_t/gap 各是什么？
- q 指接触表面点还是机器人中心目标？e_t/gap 是否与机器人半径和接触点语义相容？
- 首触前哪些阶段给了法向速度/力？ALIGN 时最终法向参考/实际速度是否为零，何时仍向物体靠近？是否有惯性/避障/控制权切换等作用？
- 接触未满足对齐条件时为什么进入推进分支？是主动 TOUCH、被动碰撞还是其他控制模块？
- 候选在固定世界中的漂移与物体运动/支持变化分别是什么，为什么更换？
- 实际侧移约 6 cm 后为何仍离候选约 21 cm？之后是回到哪里接近，第一次再接触是否真的变了？
- 哪些量属于已实现控制逻辑的确定事实，哪些只是因果假设？给每条解释对应的时间段、截图和源码位置。

输出一张顺序故障表：“时间段 → 可见中间量 → 实际执行 → 下游影响 → 尚待核验”。不要求强行选一个唯一根因；如果多个环节串联导致失败，应把串联关系画清楚。这里的“首断点”是排查顺序，不是宣称后续都正确。

## 6. 之后怎么逐步优化（本次不自动进入）

**B：用户介入后，始终围绕同一个实例迭代。** 每版说明要改变的行为和预期可见差异，保存 diff/参数与完整回放。可以修复为完成同一行为所必需的多个相互依赖环节，不机械要求“一次只改一个数”。但要解释各项作用；不要同时重做估计器、奖励、选点等无关机制。每版只跑该实例和针对改动的必要小测试，不跑全体 case。

进展逐级看：能按预期到达候选/安全接触 → 接触后持续有效推进 → 原脚本与原成功判据下 success。中间里程碑不冒充完整通过；允许后续证据否定某个候选或策略。不能通过延长脚本、修改目标/成功阈值、手工摆位或加入隐藏中心来“做实”。

**C：该实例的完整行为做通、用户确认后，再评估迁移/回归。** 次序建议镜像换面 → 原 dual → 其他 task；最终才做完整矩阵，明确报告代价。不把其他 case 的结果当作每次单实例开发的自动门槛。本任务不授权这些运行。

单实例调通只说明可实现与可诊断，不证明一般未知形状已解决或 RL 已可训练。
