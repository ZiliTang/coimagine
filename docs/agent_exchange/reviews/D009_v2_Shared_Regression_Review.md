## 2. P0确定缺陷：把同一时刻两个视角当时间差分

`unknown_shape.py:103–135`的_shared line缓存由所有机器人共用，并且逐观测立刻更新。

```
A(t)匹配line → 读取line(t-1)差分 → 缓存改为A(t)
B(t)匹配同一line → 读取A(t)差分 → dt=max(1e-6,t-t)
```

这是跨视角空间差异，不是物体运动。即使两观测几乎一致，也在凭空生成一个零速度/零角速度观测；有细小拟合差异时，则被放大为极端速度。

隔离当前SharedMotionEstimator的合成探针（不是物理轨迹）：

- 同刻rho相差1微米，生成drho≈1m/s。
- 静止线两观测法向只差1e-6rad，首拍估计omega≈+.99595rad/s；交换两观测顺序变为−.99595rad/s。
- 在世界点(2.5,2)处，该合成错误对应约±(−1.992,2.490)m/s表面速度，进入控制后会被裁剪。
- **反例边界**：理想完全一致观测、真实法向速度.1m/s的另一探针中，现有NIS会拒绝伪零，最终仍估到.1。因此不能声称所有dual都会因该bug停止，实际影响须查原始行。

最小修法：

1. `dt<=0`绝不生成运动观测，不用1e-6掩盖时间错误。同一tick重复update须幂等。
2. 每机器人/每line维护自己的时间历史，或对本tick做关联/空间融合后，统一与上一个tick的冻结缓存比较。
3. 本tick不能边算rates边覆盖大家共同使用的上一时刻缓存。
4. 同一物理线的多视角rates优先选质量最高的一份或显式相关融合，不能当多份独立证据。所有观测者的历史照常存储，避免选源切换又引入跨视角差分。
5. 至少用静止/平移/转动、重复包、交换机器人顺序的测试确认无伪运动，再接闭环。NIS拒绝不等于输入生成器正确。

## 3. P0条件缺陷：恢复动作也被RECOVER总力门控清掉

`system.py:70–82`：peer clearance正在执行时，coordinator进入RECOVER。
`mode_env.py:197–208`：此时实际输出的是PeerClearancePrefix的分离力。
`system.py:129–136`：RECOVER把**所有来源**的力都置0，包括这些分离力。

合成状态机探针：clearance.started=True且尚未finished时，coordinator确实选择RECOVER；输入分离力((1,0),(-1,0))，输出((0,0),(0,0))。
若机器人进入此条件，就可能出现“要求两机分开→恢复力清零→不能完成恢复→超时/失败”的闭锁。
这条路径在共享改动前已存在，可以被新的接近运动/感知/前馈触发；不是共享估计新增的数学性质。

**当前缺少轨迹，不能断言这就是8条dual失败的实际原因。** 但这比笼统再调FF gain更值得优先查证。
尤其前馈只在真实contact分支使用；若失败发生于首次接触前，它不是直接触发源。删除旧速度裁剪也改变了APPROACH速度，不能只看接触后FF。

改进方向：分清力的来源/控制权 `nominal / peer_separation / contact_recovery / brake`。
RECOVER阻止常规推进，但应让当前拥有控制权、已通过安全约束的恢复/制动力进入原物理限幅；EXIT不能误禁必需的制动力。
不要以关闭全部协调门控修复，不能给普通PUSH绕过安全的通道。
