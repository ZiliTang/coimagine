## 重要修正：engaged=0不等于握手从未激活

对12条hold共768个20 Hz记录重新逐项计数：

| 记录条件 | tick数 | 按0.05秒换算的记录时长 |
|---|---:|---:|
| 双方contacting_object都为真 | 2 | 0.10 s |
| 双方contact_ready都为真 | 2 | 0.10 s |
| 双方joint_active都为真 | 7 | 0.35 s |
| 双方ready_flag都为真 | 191 | 9.55 s |
| 全部engaged条件同时成立 | 0 | 0 s |

这些是日志采样口径，不是证明120 Hz物理子步中完全没有更短接触。
10/12条hold没有记录到双方同时接触；其余两条各只有1个tick。

具体反例：

- `dual_0/seed1002/d103`，日志85.25 s：双方contacting_object和contact_ready为真，joint_active为假。
  85.30 s：双方joint_active变真，但双方contacting_object/contact_ready变假。
  joint_active累计为真7个tick。握手激活确实出现，只是没有与持续双方接触重合。
- `dual_2/seed1012/d104`，日志86.40 s：双方contacting_object/contact_ready为真，joint_active为假；
  恰为窗口最后一拍，没有后续tick可判断下一拍会否激活。

源码解释：每tick先_coordinate读取先前的contact_ready，再由skill.step根据本tick观测更新
contact_ready，再推进物理和写row。因此接触就绪与联合激活存在正常的一拍时序；
row中接触来自tick开始观测，skill flags来自该次控制计算，物体位姿来自物理推进后。
这与任务书要求的严格同一tick开始快照不完全一致，应补明确pre/post阶段再用于更细的因果分析。
不能因合取条件为0就写“接触/握手条件从未建立”或“握手逻辑坏了”。

更准确的结论是：**这些hold窗口中，双方接触十分稀少，未形成与激活状态持续重合的执行条件。**
握手未触发、接触没建立、短暂接触后丢失是不同问题，应分开。

## 对RL主线的影响

暂缓用额外惩罚强化坚持。RL可能在错误几何或错误方向下尝试同推，也可能在接触建立前/后
切换；只有前一种有效准备被打断才直接支持鼓励坚持，不能把所有短段混为同一类。
本轮确实有原切换比固定动作更好的例子，因此减少切换次数不应作为训练目标的替代验收。
不扩大网络、不自动拉长保持、更不以此否定RL或联合头的全部能力。

若继续，建议先做一次范围很小的接触建立/保持审计：

1. 加入已有可成功的双推参考序列作正对照，验证接触/ready/active记录时序和engaged指标能识别稳定协作；
2. 对比一直未双侧接触、瞬间双接触后丢失两类代表窗口；
3. 在一致的tick前后时序下，列清两侧间隙、方向、接近速度、接触、ready/release/active及恢复原因；
4. 判定是所选状态/方向不适合、接触保持有问题，还是协调逻辑有问题，再选择唯一改动。

不是重新从头调控制器，也不把所有失败都归为握手。independent到达后停止仍是另一条更直接的
RL基线改进候选，但本次不同时开工，不自动发布D003。
