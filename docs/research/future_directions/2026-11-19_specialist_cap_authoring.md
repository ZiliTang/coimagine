# 从剩余失败案例中开发专用 CAP

2026-11-19 讨论 · 待实验

**研究问题。** 旧库已能解决一部分任务。给 LLM 相同的剩余失败案例和开发预算，允许它为一两个具体失败点手调动作序列，从头写出的策略能否带来更多独有成功？旧任务已经允许新 CAP 丢掉旧成功，并按轮统计新增覆盖，因此值得单独检验的是开放旧源码对作者搜索解法的影响。[原开发协议](../../agent_exchange/tasks/Random_Room_CAP_Library_20261117.md)

**机制假设。** 旧代码提供了可复用的导航和接触逻辑，也可能让作者不断微调同一种失败解法。一个单独覆盖率很低的程序，只要能解决旧库成员全部失败的场景，就有增量价值。手调序列可能只在一个初态的精确接触时机下有效，邻近复验可检验这种敏感性。

**最小对照。** 冻结同一个旧库、开发失败集合、作者模型、公共控制接口及工具知识。两组都允许专门化，目标都写成“尽可能增加旧库未覆盖的成功场景”。一组可读并修改旧策略，另一组从空白策略开始；作者看到的失败回放、交互预算和新增成员名额一致。第一轮从同一个剩余集合出发，便于配对比较。多轮时另记录两组剩余集合何时开始分化。若还要判断“明确鼓励专门化”本身的贡献，可另设提示词对照。

**怎样解释结果。**

- 开发阶段记录旧库全员失败、新成员成功的例数，以及消耗的重置、物理 ticks 和作者调用量。运行中的策略只访问合法观测和历史，场景 ID 与初态文件留作离线来源记录。
- 作者和程序冻结后，分别测原初态复现、从未展示的邻近初态、独立新场景。三项分别回答“找到了解吗”“局部稳定吗”“扩展了同分布覆盖吗”。各自报告分母、逐例新增和相同预算下的增量。
- 记录集成选择器实际保住了多少新增场景。程序库存在成功成员，与选择器能够从公开信息识别何时采用其建议，是两个需要各自验证的问题。
