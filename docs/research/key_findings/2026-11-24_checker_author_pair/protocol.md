# 检查反馈能否帮助 CAP 作者写出更好的母策略

两位独立作者从同一个保守母策略开始，使用相同的开发房间、执行器、公开观测、试跑预算和提交规范。检验作者在开发时看到程序的具体检查结果，能否使其在新房间解决更多任务，并保住起点策略已有的成功。这个起点在上一次对照中明显弱于它的前身，因此本轮同时复测较强的前身。

## 开发

- 每组一位 GPT-6.2 Sol 作者，独立上下文，每人最多 20 分钟、3 份候选。每个候选最多测试同一批 16 个开发房间，每间从初态执行一次。记录实际耗时、候选数、试跑数和可取得的 token 用量。
- 两组都获得同一公共指南、母程序、接口和开发反馈。程序可以换位、推动或停止，停等仍消耗任务预算。两位作者以房间成败为主要选版依据，同时记录动作效果和已解决房间的变化。
- 普通开发组在编写时可研究程序和公开试跑记录。检查反馈组另外可以查看宿主在开发边界发现的具体问题，包括未搜索到的可行动作和仅靠部分观测作出的否决。两位作者按相同标准定稿，宿主核对提交源码、实际出招及 campaign 封印。闭环统一运行通过核对的程序。
- 作者按时间记录怀疑哪条决策有问题、根据哪个开发实例、如何修改和复测。如果无法独立确认首个故障的发现时间，只报告记录出现的时间。

正式计时前，宿主还固定了检查反馈组可见的两份输出。一份核查 3 个公开开发边界上的完整 PUSH 菜单，另一份用 16 间已有公开轨迹，将策略申报的前向和横向位移范围与下一普通边界可见的箱心估计对照，并检查随后 120 ticks 内是否发出过所指的续接动作或已到达目标。缺少可比观测就记为未知。作者只能看到公开估计，箱体真值留在宿主侧用于最终核验。两组都能看到这些公开轨迹及相同的提交门槛。

最初的底稿在 PUSH 中途回调上有接口错误。该次准备性启动及其中一份候选请求保留在运行根目录，整批作废。修正后先逐房核对 16 个开发房间的所有实发指令、最终历史、动作承诺和事件，与历史母策略全部一致（共同起点成功 2/16）。正式阶段使用两位新作者、全额时钟和独立的 `authoring_verified/` 目录。

## 冻结评估

64 个新房间按通道几何分为无阻挡、有可动物、有静态障碍和两者都有四层，每层 16 间。对登记过的 5,984 个房间按 ID 和去掉 ID 后的内容哈希排重。房间在作者开发前冻结，评测前核对两组的最终源码。四个程序用相同的固定 72 束观测和局部坐标估计，从相同初态独立执行。保持原有正常决策与 PUSH 进度回调、动作和预算，不加顶层恢复分支。

主比较为检查反馈组与普通开发组逐房间的成败差，另分别对共同起点 P保守推进.v1 和历史较强的 P绕行.v1 计算救回、丢失与净差。报告全部四组的分母、配对不确定性、运行异常，以及推进和停滞的实测。这里的区间反映换房间的变动；每组只有一位作者，无法估计换作者带来的变动。评测完成后不按结果换版。

## 跨任务接口

在推箱观测和执行记录中检查动作前提、实测结果及可观测的后续证据。用同一检查逻辑核对合成的深柜取物案例，包括抓稳后能撤出、抓稳后被挡住和撤回空间被遮挡。分别报告哪些结论得到证据支持、哪些被反驳、哪些仍未知。此次深柜测试只检验接口，机械臂闭环效果另需实测。
