# 用故障转移图选取 CAP 开发前缀

固定对角起终点、两台机器人的初态、一个静态障碍和一个可动障碍，只改变障碍的位置。冻结开发 160 间和留出 200 间，按目标物直线平移时扫掠区域是否与静态、可动、两者或均不相交等额分层。这四类描述初始布局，场景几何合法不保证存在可行轨迹。所有房间计入闭环分母。

两组从同一通用程序（历史常规 CAP s003，固定 72 束和局部中心估计）开始。每组至多三轮，每轮最多两版同接口子程序，由 6.2-sol 编写。作者在选中的开发房间得到试跑反馈。随机组与图组共用执行器、案例配额、源码接口、反馈格式与提交规则；两组的案例由各自当前程序的表现产生。比较方法包含开发选题的后续累积效果。

候选先在作者样本从初态运行，然后将该批次最佳候选在完整开发池评估。以相对当前程序的全池净成功数严格增加作为接纳条件。各轮封存后才在相同的留出布局上评估母程序及两组各轮保留程序，报告相对母程序的逐房间救回和丢失。终点评估前不向作者反馈留出结果。单次作者开发对照不能估计作者随机性。

## 开发起点

母程序在 160 间上成功 96 间。四层各 40 间，无遮挡 35 间、仅可动障碍阻挡 27 间、仅静态障碍阻挡 23 间、两者均阻挡 11 间。两组首轮材料均为 8 个最终失败、4 个最终自然恢复的房间。图选组的 7 个失败前缀围绕同一类瓶颈，余下 1 个随机选取。

每组使用一个独立的 GPT‑6.2‑Sol high 作者会话，每轮两次提交机会，各次 360 秒，模块源码最多 10,000 字节。首个 CLI 请求在生成前因登录渠道不支持该模型而被拒，两组随后统一经支持同名模型的子代理通道启动。记录提交次数、提示字节、实际等待和仿真 ticks；精确模型 token 消耗不可用。
