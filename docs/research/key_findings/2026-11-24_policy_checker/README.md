# 交卷前检查 Python CAP 的证据和候选动作

第一版检查器能在一次普通决策上指出程序根据什么几何证据剪掉候选、是否把让行同伴固定在原地作预测，以及主动换位时是否遗漏了按程序自己的标准仍可推动的动作。它支持新作者的交卷验收，也可通过与特定源码哈希绑定的适配器审查历史程序。

## 给新作者的接口

作者继续用 Python 编写策略。一份源码须包含审查规则声明 `POLICY_CHECK_RULES`、供实际选动作与离线审查共用的 `review_push`，以及记录真实决策依据的 `audit_policy`。宿主解析静态声明，逐项遍历当前公开菜单，并在独立的隔离调用中核对同一程序实际给出的第一条命令。检查器可以拦住“可见下界不足，因此物理上一定放不下”的声明。若作者明确说“我没有把握，所以改做换位”，会保留相应告警供局部实测。规则声明与内部计算如实对应，仍是使用这种作者接口的前提。

已用公开初态走通示例策略的收卷和文件哈希复核。提交保存源码、输入、逐项判断、告警和宿主检查版本；接口缺失、数据无效或硬性矛盾会阻止收卷。这个程序示例仅演示可见推面的证据使用。[作者指南](../../../../experiments/planar_tasks/authoring_v2/checked_policy_guide.md) · [完整 Python 示例](../../../../experiments/planar_tasks/authoring_v2/checked_policy_example.py) · [示例提交清单](../../../../outputs/semantic_rl/cap_policy_checker_v1/example/accepted/manifest.json)

## 冻结 P保守推进.v1 的检查结果

开发房 003 的 tick 50 用来设计规则。其余检查点来自此前已评过的 `safe_nominal_v1_confirm` 房间。先按已有的四种初始通道类型，各取编号最小的两间，再取原 P 在各房间的第 1、第 6 个非初态、普通决策边界发出的目标推动。选择过程独立于本次检查器的结论。每个前缀都在相同公开历史上重建保守 P 的记忆并核对提案，后续物理证据只用于离线分析。[选样清单](../../../../outputs/semantic_rl/cap_policy_checker_v1/selection.json) · [17 个边界逐项结果](boundaries.csv)

| 检查项 | 003 已知案例 | 另外 8 间，16 个前缀 |
|---|---:|---:|
| 核对的目标平移 PUSH 组合实例 | 32 | 536 |
| 用不充分的可见宽度作保守剪枝的前缀 | 1/1 | 15/16 |
| 以静止预测让行同伴并影响否决的前缀 | 1/1 | 0/16 |
| 放弃推动时漏掉按自身规则通过项的前缀 | 1/1 | 0/16 |
| 对已申报行为发现硬性矛盾的前缀 | 0/1 | 0/16 |

003 实际只提出了 4 个推动，完整菜单中有 16 个本可通过审查的双推组合。另 16 个前缀有 15 个已选中推动，提前结束搜索是允许的；唯一改做其他动作的前缀，完整菜单确实是 0/32 通过。全部 8 间的第一个入选边界都在 tick 40，七间的第六个在 tick 136，所以这些频数不能当成 16 种独立的故障，更不能用来估计策略在新任务的误报率。

## 与已执行动作的物理效果核对

在每个前缀只有旧 P 当时实际执行的命令有对应实测。组内有 8/16 个新 P 的完整首条命令与旧 P 完全相同，其余前缀的机器人动作或时长有差异。按旧 P 的动作编号对核对，15/16 通过新 P 的审查，其中 14 个在旧 P 实际执行期间让箱子净靠近目标至少 2 cm。

**001 房间 tick 136** 更能说明检查器的边界。新 P 以“前方扫掠余量不足”拒绝旧动作，同一菜单内也找不到其他通过项。旧 P 在此处实际执行了 29 ticks，箱子净靠近目标 **11.17 cm**，采样的物理阶段首末未见箱体接触静态物。这说明可以检出内部一致却可能过于保守的局面。一次局部推进无法判定该动作在所有可能后果下的碰撞风险。536 个动作组合实例中有 520 个缺少同一前缀的实际执行结果。[物理核对及测量分辨率](../../../../outputs/semantic_rl/cap_policy_checker_v1/physical_checks.json)

现有证据支持把检查器用于帮作者挑选值得复查的前缀。作者收到反馈后是否能在相同开发预算内少丢成功路线、提高整局成功率，需要另作作者对照。
