# CoImagine：快速代码审查材料交接要求
版本 v1｜2026-10-12

## 1. 当前任务

暂停新方法开发。将当前实现与已有实验证据打包，供外部审查者做一轮快速代码审查。

本轮只允许：
- 读取代码、Git 状态与已有结果。
- 复制文件、导出版本信息、生成目录索引与压缩包。
- 为打包编写独立辅助脚本，并验证包内文件完整性。

本轮不要：
- 修改、修复或重构生产代码。
- 训练模型、生成新的实验数据、重跑完整实验。
- 实现确定性简化 Grid、多尺度预测或新的评分。
- 为消除审查疑点而先改掉原实现。
- 只交付文字综述、代码截图、函数节选或 diff。

如发现疑似 bug，记录“疑点—文件/函数—依据”，保留代码原状。不要将猜测写成已确认原因。

交付一个 ZIP：CoImagine_review_bundle_v1.zip。
ZIP 内保留仓库相对路径。不要创建 Git 提交来包装此次交接，不上传远程服务。

## 2. 必须包含的源码与配置

以当前工作区实际文件为准，包括未提交修改和未跟踪的新文件。git archive HEAD 不能单独满足要求。

优先复制整个 src/coimagine/ 源码目录：它规模若正常，这比人工挑选函数更可靠。另包含以下文件及其直接本地依赖：

所有文件必须为原始可读文本或原始二进制文件，不能用描述代替。

## 4. 新增三份简短交接文件

放在 ZIP 顶层 review/ 中。

### 4.1 REVIEW_INDEX.md

不超过 1000 中文字，不复述研究背景。回答以下问题，并给出当前文件路径及函数名；能确定时附行号。

1. 旧 Grid 哪些量未知？给定完整状态/参数后转移是否确定？是否存在观测、反馈或动作随机性？
2. “观测一致世界集合”如何生成和赋权？采用什么先验、哪些观测历史？模型侧与参照侧是否使用相同分布？不能只回答“精确期望”。
3. 当前诊断调用的是原边缘状态传播，还是逐参数条件状态传播？与此前 conditional_planner 的关系是什么？
4. Grid 的 J_hat/J_ref 各如何计算？累积代价、成功吸收、距离、概率期望是否同口径？这次评分与历史 planner 的差别是什么？
5. 连续环境“含通道可通行性的几何代价”完整公式在哪？是否有特定通道方向、任务阶段或场景 ID 分支？
6. 候选是在当前状态生成一次，还是在预测节点重新生成？两机器人动作如何组合？128 的上限限制单节点、完整序列还是整次规划？
7. beam 保留什么、何时截断、按什么排序？各候选是否累计此前的时间与控制成本？并列如何处理？
8. export/restore 实际恢复了什么？物理引擎隐藏状态、控制器状态、成功保持计时器、随机数与前缀如何处理？
9. witness 是独立指定序列，还是来自 MPC 成功轨迹？是否被候选生成器或测试代码读取？
10. 当前是否已有单机器人贡献对照？没有就写未做，不新增实验。

回答不确定时明确写“不确定/未记录”，不要根据预期补写实现。

### 4.2 SNAPSHOT.json

记录：
- 打包时间与时区。
- 当前 HEAD。
- git status --short 的结果。
- Python 与关键依赖版本（读取已有 manifest 与实际环境，若不一致同时列出）。

- 旧检查点路径与 SHA256。
- 打包实际包含的结果目录。
- missing_files：本要求中未能找到的文件及原因。

- git diff --binary HEAD 可保存为 working_tree.patch，但新文件仍须完整复制。

文件哈希单独放 SHA256SUMS.txt，覆盖全部实际打包文件（排除该哈希文件自身）。不要包含压缩包自身。

### 4.3 RUN_REVIEW.md

引用现有测试结果时注明来自哪次运行。没有本轮重新运行，就明确写“本次打包未重跑测试”。

## 5. 打包与范围限制

- 使用 ZIP，源码保留完整路径与内容；不要把所有代码合并成一个超长 Markdown。
- 不包含 .git/、.venv/、node_modules/、缓存、全部历史输出或大型无关数据。
- 不包含 .env、密钥、令牌、账号认证、SSH 文件、含凭据的远程 URL。
- 只复制项目需要的文件。符号链接不得将仓库外目录意外打包。
- 目标压缩后不超过 30 MB。若超出，先删除非必需媒体和重复产物，不删除关键源码或逐候选标量数据。
- 仍超出时分为 code.zip 和 evidence.zip，附映射；不要为了凑大小静默丢材料。
- 缺文件就记录，不凭空创建看似真实的原始结果。
- 不批量安装新依赖，不改变当前实验环境。

打包完成后仅做：
1. 验证 ZIP 可读取。
2. 验证清单中的文件存在且哈希一致。
3. 验证关键源码、检查点和原始结果已包含。
4. 查看 git diff/status，确认除打包辅助文件外没有修改生产代码。

这些是文件完整性检查，不是重新验证实验。

- 压缩包路径与大小，方便用户上传到审查会话。

- 缺失材料列表（没有则写无）。
- 是否修改生产代码、是否重跑实验。
- 最多三条自行发现但尚未确认的疑点。

完成后停止。等待外部代码审查结果，再决定下一轮实验任务。
